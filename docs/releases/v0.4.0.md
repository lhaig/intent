# Intent v0.4.0 — cross-package generics, end to end

A minor release on top of v0.3.1. It adds one new piece of language surface —
module-qualified generic and variant construction — and then carries that surface all the
way through the *self-hosted* compiler, closing the last stage2 parity gap on cross-package
generics. The `stage1 → stage2 → stage3` bootstrap fixpoint still holds: `make
bootstrap-stage3` is **4/4 EQUAL** at this release.

## Language: module-qualified generic and variant construction

The qualified forms now work end to end:

```intent
pkg.Pair<Int>()       // module-qualified generic constructor
pkg.Variant()         // module-qualified enum variant
pkg.Enum.Variant()    // fully-qualified enum.variant
```

Previously only the bare forms parsed; the qualified forms failed to parse or were rejected
by the checker. This release wires them through the parser (`MethodCallExpr` gains a
`TypeArgs` field), the checker (generic constructors, generic function calls, and enum
variants resolve across a module qualifier), and the IR (a qualified generic/variant call
lowers identically to its bare form, so monomorphisation and variant construction stay in one
place — no backend change).

## Self-hosting: the stage2 compiler now covers cross-package generics

The self-hosted (Intent) backend already monomorphised generic *entities*; this release
closes the remaining cross-package/generics gaps so stage2 emits Rust byte-for-byte identical
to stage1 (Go) across the whole surface — see [ADR 0061](../decisions/0061-cross-package-codegen.md):

- **Generic free-function monomorphisation** — a call like `identity<Int>()` now rewrites to
  the mangled global (`identity__Int(...)`) and emits the specialised function, mirroring
  stage1's `monomorphizeFunction`. This was the last stage2 self-hosting-parity gap.
- **Unqualified imported-call mangling (`funcOrigins` parity)** — an unqualified call to a
  function imported from a dependency (`helper(...)` rather than `pkg.helper(...)`) now takes
  the *defining* module's prefix instead of the calling module's, so it compiles.
- **Entry-only generic monomorphisation** — a generic instantiated only in the entry module
  (a consumer constructing a dependency's `Pair<Int>`) now emits the struct as well as the
  constructor call.
- **Formatter fidelity** — the self-hosted formatter no longer drops `<Int>` from
  `pkg.Pair<Int>()` (it now emits `MethodCallExpr` type arguments).

## stage1 code generation

- Corrected cross-package **enum, generic, and mangling** emission, and mangling of
  unqualified imported function calls.

## What's next

The self-hosted compiler currently bootstraps the **Rust** target only; extending it to the
JavaScript and WebAssembly backends — so the whole toolchain self-hosts on every target — is
the next major milestone. Also on the near roadmap: a versioned package registry (today's
dependencies are git/path only), verification-aware contract stripping
(`--strip-contracts=verified`), and closing the self-hosted checker's sound-false-negative
tail.

## Upgrading

`intentc` takes its version from the git tag at build time (`-ldflags -X main.version`). No
source or config changes are needed to upgrade.

## Known limitations

- The self-hosted compiler still emits the **Rust target only**; the JS/WASM backends remain
  Go-only.
- ADR 0061 records a latent stage1 hazard the parity audit surfaced: monomorphisations emit
  in Go-map order, so a module with **2+ distinct generics** has a non-deterministic emit
  order. No program in the corpus triggers it, and the bootstrap fixpoint is unaffected, but
  it is tracked for a future fix.
- The self-hosted checker's documented tail of sound-false-negative diagnostics is unchanged
  from v0.3.1 (see `prds/backlog/prd-phase-58-checker-parity-tail.md`).
